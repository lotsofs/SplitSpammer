# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

SplitSpammer will be a LiveSplit layout component (.NET Framework 4.8.1 class library, WinForms) that auto splits GTA San Andreas. It reads the game's memory itself, has a settings tree you can collapse and expand, splits through LiveSplit's timer, and is unit-tested without the game. It replaces `GTASA.asl`, which grew too large for one ASL file (ASL has no includes and can't be tested without LiveSplit and the game), and the auto-splitting runtime was ruled out because its settings dialog can't collapse.

**Status: early.** The component loads, starts and resets the timer on a new game and splits on In the Beginning (all seen in LiveSplit), Big Smoke (seen live), Ryder and the Firefighter side mission (neither seen live yet, see docs/Live.md): a factory, a component with a poll thread that reads the game, and a settings panel with the game status and the settings tree. All planned work is tracked as items, each with its design written down.

## Build and deploy

```sh
dotnet build LiveSplit.SplitSpammer.sln -c Debug     # or -c Release; add -p:LiveSplitDir=<folder> for another LiveSplit
deploy.cmd                                             # build the component, then copy it into LiveSplit's Components folder; deploy.cmd Release for Release
```

- `deploy -r` builds, then force-kills LiveSplit if it runs (unsaved changes in it are lost), copies the DLL and starts LiveSplit again; it reopens its last layout. `deploy -p` builds `Preview\` and opens the settings panel in a window of its own, without LiveSplit or deploying; its settings are kept in `%TEMP%\SplitSpammerPreview.xml` between runs (delete it to start fresh). The preview does not prove the component loads in LiveSplit. The flags combine with Debug or Release.
- Without `-r`, `deploy.cmd` refuses to run while LiveSplit is running (LiveSplit locks the DLL), builds the project, and copies `bin\<config>\LiveSplit.SplitSpammer.dll` into `Components\` in the `LiveSplitDir` folder. It is a batch file because PowerShell scripts are disabled on the user's machine, and it keeps CRLF line endings. Run it from PowerShell (`.\deploy`), cmd or Git Bash (`cmd //c deploy.cmd`).
- An SDK-style csproj (C# Dev Kit can't load an old-style one, and then F12 finds nothing): `.cs` files are included automatically, except under `Preview\`, `Tests\` and `reference\`, which the csproj removes. `GenerateAssemblyInfo` is off because `Properties\AssemblyInfo.cs` holds the attributes, and `AppendTargetFrameworkToOutputPath` is off so the DLL stays in `bin\<config>\`. It targets .NET Framework 4.8.1, because LiveSplit does from 1.8.30; with a lower target MSBuild can't resolve its DLLs. `dotnet build` works without Visual Studio as long as the 4.8.1 targeting pack is installed.
- `LiveSplit.Core.dll` and `UpdateManager.dll` come from the `LiveSplitDir` folder, by default `..\..\Programs\Streaming\LiveSplit` from the repo, which is `D:\Programs\Streaming\LiveSplit`. Both are `<Private>False</Private>`, so `bin\<config>` holds only the component's DLL and PDB. Give a full path without a trailing backslash to `-p:LiveSplitDir`.
- The build has no warnings, so any warning is new. There is no test project yet (item TST). Until then, a headless check can be made with a scratch program that loads the DLL, builds a `LiveSplitState` the way OutputToFile's `Tests\TestRun.cs` does, and calls the factory and component members.

## Adding a mission

Each mission still to port has its own item in [docs/TODO.md](docs/TODO.md), and [docs/porting.md](docs/porting.md) gives the steps every port follows (settings, leak names, read order, the comparison with the ASL, docs) and the ASL behaviour they rely on. A mission is one file in `UI\Components\Missions\`, a class implementing `IModule`, as `InTheBeginning.cs` does; add it to `Modules.All` in `UI\Components\Modules.cs`. `AddSettings(tree)` adds its settings with `tree.Add(id, label, default, tooltip, parentId)`, in the ASL's order, with the ASL's label, default and tooltip and an id of our own (see Conventions); the id is also the split id. `AddChecks(engine)` adds every watcher its check reads, shared ones too (`engine.Watchers.AddScmGlobal(name, n)`; there is one watcher per address, so a name for an address already watched gets the same watcher, and adding a name again does nothing), the mission's thread and marker text (`engine.RegisterThread(thread, id)`, `engine.RegisterMissionName(text, id)`; the engine splits them and keeps `engine.LastStartedMission` for the checks, cleared once the mission's thread has ended) and a check that returns a split id or null. A story mission keeps its frame in a `StoryMission` (`UI\Components\Missions\StoryMission.cs`, the ASL's `RegisterMissionBasics` and `ValidateMissionProgress`): `AddBasicSettings(tree)` first and `AddPassedSetting(tree)` after the events in `AddSettings` (last, except where the ASL adds events after the pass, as Big Smoke does), `Register(engine)` in `AddChecks` (it also registers the marker with the thread, so a marker whose title the replay trick skipped still splits as the mission starts; a check that splits on a marker entry reads `engine.MarkerEnteredThisTick`, not `missionStartText`), and `InProgress(engine, chain, before, after)` as the check's first test (`engine.MissionInProgress` takes the arguments raw, for checks that don't fit). Copy the ASL's order of reads and early returns exactly: which watchers get read in a tick decides their Old value. A split the ASL lacks can be queued with `engine.TrySplit` in the tick of an ASL split instead of waiting behind its `return`, as long as what follows reads no watcher the ASL wouldn't read in that tick; test an event, not a state (`engine.HasStarted(script)`, not `IsRunning`, for a script starting), or the check returns its id every tick the state holds. The engine only lets a split through when its setting and all its ancestors are checked. The layout stores only settings that differ from their default, so adding one needs no migration; a removed id is ignored when loading.

## Threads

- LiveSplit's timer events can run on another thread, so the handler (`State_OnReset`) only counts with `Interlocked`; the poll thread acts on the count. A handler that throws there closes LiveSplit.
- The reader, the watchers and the engine belong to the poll thread (`EnginePoller`). The settings control, `TimerModel` (reset, start, split) and `Update()` belong to the UI thread; the poll thread posts the tick's timer actions to it through the captured `SynchronizationContext`. The only data crossing is the `volatile` settings snapshot and the reader's `volatile` status.
- `Update()` runs every frame: keep it cheap. Every poll step is wrapped so an exception is logged, never thrown into LiveSplit. `Dispose()` stops the thread. See [docs/architecture.md](docs/architecture.md).

## Conventions

- Follow OutputToFile's code style: tabs for indentation, namespace `LiveSplit.UI.Components.SplitSpammer`, and thread rules (LiveSplit's event handlers may run on another thread, so they only count; the work happens elsewhere).
- Only GTA SA PC version 1.0 is supported. It is recognised by the main module's size (18313216) or the int 38079 at `+0x4245BC` or `+0x42457C`; the size is needed because the int isn't there while the game checks the CD. The game's memory is read through `IGameReader` (`ProcessGameReader` uses its own ReadProcessMemory calls, not LiveSplit.ComponentUtil, which is inside LiveSplit.Core.dll). SCM globals are at module `+0x649960 + n*4` and mission locals at `+0x648960 + n*4`.
- Split and setting ids are our own, not the ASL's: the mission's script name as the game has it in memory (`intro` for In the Beginning, `intro1` for Big Smoke) plus a camelCase event that says what the player sees or the game does (`intro_groveStreetLinePlayed`), and a watcher name is never reused as an id. Every story mission's three common splits are `<mission>_markerEntered`, `<mission>_started` and `<mission>_passed` (`StoryMission` builds them). The leak's variable names (`reference\scm_leak.txt`, mapped to `$n` by the "GTASA Global Variable Table 2022" sheet) are a good source for names. A watcher on an SCM variable has the leak's exact name (`w.AddScmGlobal("voice_over_at_hub", 54)`), an array element with its index as the leak writes it (`"sw4_hood_dead[3]"`); other watchers (not SCM variables) are camelCase (`playingTime`). Labels, defaults and tooltips follow the ASL, but labels are in sentence case: only the first word and proper names (missions, people, places) are capitalised ("Mission marker entered", "Grove Street cutscene start"). A label's verb says when it splits: "-ing" as the action starts ("Leaving CJ's house", when the interior number changes as CJ steps into the door's marker, seen by the user in CJ's house), "-ed" once it is done ("Left CJ's house", outside with Ryder's marker shown). At a marker that fades to a cutscene, "Arriving at" is as the marker is entered and the fade to black starts, "Arrived at" once it has faded and the next cutscene starts; rename an ASL label that gets it wrong.
